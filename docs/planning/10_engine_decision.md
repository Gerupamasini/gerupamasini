- 状態: **決定（2026-10-12）: Steam 版も Three.js のまま出す（選択肢 A を土台にし、B の一部は後から足す）。Electron で包む。** スマホ版も同じコードから作る。2026-10-11 に決めた C（UE5）は取り消し、UE5 版のリポジトリ [Gerupamasini/UE5HigataZukan](https://github.com/Gerupamasini/UE5HigataZukan) は参考として残して開発を止める

> 決定の経緯:
> - 2026-10-11: §5 の案では B と C を試作で比べてから決めるつもりだったが、比較を待たずに Steam 版は C（UE5）に決め、別のリポジトリで移植を始めた。
> - 2026-10-12: Steam 版も Three.js のまま出すことにした。目標を「世の中に多くある PC でも動く、いちばん良い画」と置き直した（§8）。UE5 版で作った潮汐・太陽の計算の C++ 移植と照合テスト、走水の地形の取り込みなどは、UE5 版のリポジトリに残っている。

## 1. 背景

『干潟図鑑』は Three.js 0.186（WebGLRenderer）+ TypeScript + Preact の Web ゲームで、GitHub Pages で公開している。次の 3 つを目標にする。

1. **Steam でリリースする**（Windows、Steam Deck）
2. **世界最高のグラフィックで干潟を体験させる**
3. **スマホ版も出す**（iOS / Android）

今のコードの規模と性質（2026-10-11 時点）:

| 項目 | 値 |
|---|---|
| コード | 約 5.7 万行。うち生物 4.0 万行、世界 7.7 千行、アプリ 4.2 千行、UI 3.3 千行、描画 0.5 千行、潮汐 0.3 千行 |
| 自作シェーダー | `onBeforeCompile` 51 か所（19 ファイル）、`ShaderMaterial` 約 19 個、GLSL の `main` 52 個 |
| 生物モデルの作り方 | **GLB**: マハゼ・エドハゼ・ヒメハゼ（`tools/models/*/build.mjs` で生成）、シロチドリ、タモ網などの道具。**実行時に TS で生成**: アカエイ、イシガレイ、アラムシロ、マガキ、エビ 2 種、ヨウジウオ、アミメハギ、ハク、アサリ・ハマグリ、ユビナガホンヤドカリ（8.4 千行）、カニ・ゴカイなど |
| エンジンに依存しないもの | `public/data/`（種、行動ツリー 14 本、地図、潮汐、道具、文言 ≒ 1 MB）、zod スキーマ、潮汐モデル `src/tide/`、行動ツリー（`Vector3` だけに依存） |
| 素材 | GLB 55 個で 276 MB（無圧縮テクスチャ）、地形 PNG 0.8 MB |
| 開発体制 | 人間 + Claude による反復開発。**すべてがテキスト**で、差分のレビューも、ヘッドレス Chromium でのスクリーンショット検証も自動でできる |

## 2. 判断の基準（重い順）

1. **干潟の画の上限**: 濡れた泥への空の映り込み（低い角度の鏡面反射）、薄い水膜、細かな凹凸（波紋・巣穴・糞塊・足跡）、浅い水の流れ込み、生物の SSS と濡れた光沢、大域照明
2. **スマホで動くか**と、PC 版と同じ中身を出せるか
3. **今の資産をどれだけ使えるか**（とくに 4 万行の生物の作り込み）
4. **AI と一緒に開発できるか**: テキストで差分が見えるか、ヘッドレスで自動検証できるか
5. Steam・ストア対応の手間（Steamworks、Deck、Cloud、パッケージ）
6. 費用とライセンス、開発期間

## 3. 選択肢

### A. Three.js（WebGL）のまま、Electron で Steam、Capacitor でスマホ

- 画の上限: 中〜高。レイトレーシングはなく、反射は画面内の情報と平面鏡の組み合わせ。カスケード影も自前で作る必要がある
- スマホ: ◎ 今の作り（タッチ操作、画質プリセット 4 段）がそのまま使える
- 資産: ◎ 全部使える
- AI 開発: ◎
- Steam: Electron + steamworks.js などで対応。オーバーレイの表示など、細かい挙動は要検証。Tauri は Linux（SteamOS）で WebKitGTK になり WebGL の性能が不安なので、Electron を推す
- 弱点: 「世界最高」とは言いにくい。Electron の分のメモリと容量が上乗せになる

### B. Three.js を WebGPURenderer + TSL に移し、Electron と Capacitor

- 画の上限: A より上。コンピュートシェーダーで浅水シミュレーション、GPU パーティクル、地形の変形ができる。ハードウェアのレイトレーシングは WebGPU に無い（2026 年 10 月時点の理解。要確認）
- スマホ: ○ 対応ブラウザー・WebView では WebGPU、それ以外は WebGL2 にフォールバック。iOS の WKWebView での WebGPU の状況は要確認
- 資産: ○ ロジックとデータはそのまま。**GLSL 約 70 か所を TSL に書き直す**必要がある
- AI 開発: ◎
- 弱点: A と同じく画の上限は UE5 に届かない。TSL と WebGPURenderer はまだ変化が速い

### C. Unreal Engine 5

- 画の上限: **最高**。Lumen（大域照明と反射、ハードウェアのレイトレーシング）、Nanite（泥の細かな凹凸を形状そのもので持てる）、仮想シャドウマップ、Niagara、水のシステム、Substrate 材質
- スマホ: △ モバイル用の描画は別物で、Lumen と Nanite は基本的に使えない（高性能端末向けの対応状況は要確認）。PC 版とスマホ版で見た目に大きな差が出る。アプリも大きくなる
- 資産: △ データ（JSON）、潮汐の計算、行動ツリーの設計は移せる。GLB の 3 種と道具は読み込める。**実行時生成の生物 11 種以上と自作シェーダーは作り直し**。手続き生成のコードは「glTF を書き出すツール」に変えれば再利用できる
- AI 開発: △ アセットとブループリントがバイナリで、差分が見えない。**ロジックを C++ に寄せ、ブループリントを最小にすれば**ある程度保てる。自動検証はヘッドレス描画とテストの仕組みを作り直す必要がある
- Steam: ◎ Steamworks、Steam Deck（Proton）、DLSS / FSR などが標準でそろう
- 費用: 売上が 100 万ドルを超えるまでロイヤリティなし（その後 5%）。条件は契約時に確認する

### D. Unity 6

- 画の上限: 高。HDRP は高品質だが、今後の描画パイプラインの方針（URP への統合）は要確認。PC 用とスマホ用でパイプラインを分けることになる可能性がある
- スマホ: ◎ 実績が多い
- 資産: C と同じく作り直し。C# はテキストで、シーンも YAML なので AI 開発は C より楽
- 弱点: 「世界最高の画」を狙うには、描画の自作部分が C より多くなる

### E. Godot 4

- AI 開発（全部テキスト）とスマホは良いが、画の上限が目標に届かない。**候補から外す**

| 基準 | A WebGL | B WebGPU | C UE5 | D Unity 6 |
|---|---|---|---|---|
| 画の上限 | △ | ○ | ◎ | ○ |
| スマホ | ◎ | ○ | △ | ◎ |
| 資産の再利用 | ◎ | ○ | △ | △ |
| AI 開発 | ◎ | ◎ | △（C++ 中心なら ○） | ○ |
| Steam 対応 | ○ | ○ | ◎ | ◎ |

目標の 1（世界最高の画）と 2（スマホ）は、どの選択肢でも同時に最高にはならない。**どちらを優先するか**が判断の核心になる。

## 5. 当初の案（2026-10-11、採らなかった）

**すぐには移行しない。6〜8 週間の「縦切り試作」で B と C を同じ場面で比べてから決める。**

試作の題材: **走水の干潮、夕方、アマモ場の縁**。マハゼ（GLB）とアカエイ（手続き生成）を置く。

| 確かめること | 合格の目安 |
|---|---|
| 濡れた泥への空と夕日の映り込み、乾いていく様子 | 写真と並べて見分けにくい（スクリーンショットで判断） |
| 上げ潮が澪筋から広がる浅い水 | 不自然な継ぎ目や飛びがない |
| 足跡・砂煙・アカエイの砂潜り | 足跡に水がしみ出す |
| 性能: 中位 GPU（RTX 3060 / RX 6600 程度）、Steam Deck、中位スマホ | 1080p で 60fps ／ Deck 800p で 30fps ／ スマホで 30fps |
| アカエイの移植にかかった日数 | 残り 10 種以上を移す見積もりの根拠にする |
| AI と開発したときの速さ | 同じ変更（例: 材質の調整）の往復にかかる時間 |

判断の分かれ目:
- C が画で明らかに勝ち、移植の見積もりが許容範囲なら → **C（UE5）で Steam 版**。スマホ版は「今の Web 版をアプリ化」するか「UE5 のモバイル版」にするかを試作の数字で決める
- 差が小さい、または移植が重すぎるなら → **B（Three.js + WebGPU）で Steam もスマホも 1 本のコード**

どちらに決まっても無駄にならない作業は、試作と並行して進める（[09](09_steam_readiness_audit.md) の §8 の 4 と 5）:
- 効果音と環境音（現地録音）
- 文言の文言表への移動と英訳、種データの翻訳
- 日本時間をどう扱うか（海外のプレイヤー向け）の決定
- テクスチャの元素材の整理と圧縮パイプライン
- 実機での性能計測の方法

## 6. 結果として起きること

- [09](09_steam_readiness_audit.md) の §8 の 1〜5 をそのまま進める（パッケージ化、入力、UI、音と文言、圧縮と性能計測）
- Steam 版・Web 版・スマホ版は 1 本のコード。違いは起動のしかた（Electron / ブラウザー / アプリの WebView）と、画質の初期値だけにする
- 画質を上げる機能は**画質の段階で切り替えられる**形で足す。上の段階だけで使う機能が、下の段階（スマホと内蔵 GPU）の速さを落とさないようにする
- 手続き生成の生物（約 4 万行）はそのまま使う。UE5 で必要だった「glTF を書き出すツール」への作り替えは要らない
- WebGPU（選択肢 B）は、§8 の 4 の条件がそろってから考える

## 7. 未確認の事項

- Electron での Steam オーバーレイの安定性（steamworks.js など）
- Steam Deck（SteamOS + Proton、または Linux 版の Electron）での WebGL2 の性能と、GPU のブロックリストの扱い
- 実機（内蔵 GPU、GTX 1650 級、RTX 3060 級、Steam Deck、中位スマホ）での fps。**まだ 1 台も測っていない**
- WebGPU のハードウェアのレイトレーシング対応の予定
- iOS と Android の WebView での WebGPU の状況

## 8. Three.js で画を詰める方針（2026-10-12）

目標: **世の中に多くある PC で動き、上位の GPU ではさらに良くなる画**。画の「上限」を UE5 と比べるのではなく、干潟らしさ（濡れた泥、薄い水膜、乾き、浅い水、細かな凹凸）を、どの段階の GPU でも出すことを優先する。

### 8-1. 狙う機材（目安。実機で測って直す）

| 区分 | 機材の例 | 画質 | 出力の解像度 | fps |
|---|---|---|---|---|
| 内蔵 GPU | Intel Iris Xe、Radeon 680M | 低 | 1080p（内部はその 50〜67%） | 30 |
| Steam Deck | | 低〜中 | 1280×800 | 30〜40 |
| 下位の単体 GPU | GTX 1650、RX 6400 | 中 | 1080p | 60 |
| 中位の単体 GPU | RTX 3060 / 4060、RX 6600 | 高 | 1440p | 60 |
| 上位の単体 GPU | RTX 4070 以上 | 最高（新設） | 4K（内部は 67〜77%） | 60。写真モードではパストレーシング |
| 中位のスマホ | | 超軽量〜低 | 端末まかせ | 30 |

Steam のハードウェア調査では、1080p と、GTX 1650・RTX 3060 級までの GPU が多数を占める（数字は出す前に最新の調査で確かめる）。

### 8-2. 進める順番

1. **土台（どの段階にも効き、性能の余裕を作る）**
   - テクスチャの圧縮: GLB のテクスチャを KTX2（Basis Universal）に、形状を meshopt に。276 MB を小さくし、VRAM と読み込み時間を減らす
   - 拡大: 内部の解像度を下げて描き、AMD FSR 1（EASU で拡大、RCAS で輪郭を立てる。MIT ライセンスのシェーダーだけで動く）で出力の解像度に戻す。今はブラウザーの単純な拡大に任せている
   - 動的解像度: GPU の時間を測り、目標の fps を割りそうなら内部の解像度を下げる
   - 画質の自動設定: GPU の名前から推す今の方法（`Renderer.ts` の `weakGpu`）をやめ、初回に短い計測をして段階を選ぶ
   - 性能の計測: `EXT_disjoint_timer_query_webgl2` で描画の各段の GPU 時間を取り、画面と記録に出す
   - Electron の起動設定: 高性能な GPU を使う、GPU のブロックリストを無視する、裏に回ったときの速度制限を止める
   - 進み具合（2026-10-12）: Electron の起動設定を除いて入れた。中身と確かめ方は [グラフィックの土台](../quality/graphics.md)
2. **干潟らしさ（費用の割に効く）**
   - 乾き具合: 潮が引いてからの時間と、地形の高さ・澪筋への近さから「濡れ」を計算し、泥の粗さ・色・水膜の反射に効かせる
   - 色づくり: ACES から AgX に替え、色の調整表（LUT）を足す。夕方の空と濡れた泥の色を写真に寄せる
   - TAA（時間方向のアンチエイリアス）: 泥の細かな凹凸、アマモ、網のちらつきを抑える。FSR 1 の前に置く
   - 影: カスケード影（近くは細かく、遠くまで届く）と、足元の接触影
3. **上位の段階だけ**
   - GTAO（環境光の遮蔽）、SSR（画面内の反射。画面外は空で補う）
   - GPU での浅水のシミュレーション（上げ潮の流れ込み、泡、水底の光の揺らぎ）
   - 波紋や足跡の視差による凹凸、大気の散乱
   - 写真モード: three-gpu-pathtracer で静止画をパストレーシングする（自作シェーダーの材質は、写真用の材質に置き換えて渡す）
4. **WebGPU（選択肢 B）に移る条件**: GLSL 約 70 か所の TSL への書き直しが要るので、次がそろってから考える。(a) 計測で WebGL2 の限界（コンピュートが無いことなど）が画の妨げになっているとわかる、(b) WebGPURenderer と TSL の変化が落ち着く、(c) Electron と Steam Deck で WebGPU が安定して動く

### 8-3. 守ること

- どの機能も**画質の段階で切り替えられる**ようにし、スマホと内蔵 GPU で使う段階（超軽量・低）の重さを増やさない
- 足すたびに、ヘッドレス Chromium でのスクリーンショットと、計測の数字で前後を比べる
- 写真との並べ比べ（走水の干潮、夕方、アマモ場の縁）を画の合格の目安に使う（§5 の表の上 3 行を引き継ぐ）
