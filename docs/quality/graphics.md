# グラフィック（土台と干潟らしさ）

[判断記録](../planning/10_engine_decision.md) の §8-2 の 1「土台」（世の中に多くある PC で、画を落とさずに速く描くためのもの。§1〜4）と、2「干潟らしさ」（§5〜）の記録。土台はスマホ（タッチ端末）の動きを変えていない。

| 何を | 効果 | どこ |
|---|---|---|
| モデルの圧縮（KTX2 + meshopt） | テクスチャの GPU メモリが約 1/4、形状のファイルが約 1/3 | `tools/models/pack/`、`src/assets/models-packed/`、`ModelLoader.ts` |
| FSR 1 での拡大 | 内部の解像度で描いた干潟を、ブラウザーの単純な拡大ではなく FSR 1（EASU + RCAS）で画面の解像度に戻す | `src/render/Fsr.ts`、`Upscaler.ts`、`FieldRenderer.ts` |
| 動的解像度と GPU 時間の計測 | 目標の fps を割りそうなら内部の解像度を下げ、余裕が戻れば上げる | `GpuTimer.ts`、`DynamicResolution.ts`、`Renderer.ts` |
| 画質の自動設定 | 初めて干潟に入ったとき、その PC で実際に測って段階を選ぶ | `AutoQuality.ts`、`App.ts` の `stepAutoQuality` |
| 乾き具合 | 潮が引いてからの時間・日差し・底質で、泥と砂が乾いていく（水膜のつや、暗さ） | `src/world/WetDry.ts`、`Terrain.ts` |
| 色づくり（AgX） | 夕日など明るく色の強い光の色相を保つトーンマッピング。全経路で同じ式 | `src/render/ToneMapGlsl.ts` |
| TAA | 動いているときの細かなちらつきを抑える（PC、中・高・最高） | `src/render/Taa.ts`、`FieldRenderer.ts` |
| 影 | 近くの影を細かく、遠くの物と地形（土手）の影をマップ全体に | `Sky.ts`、`src/world/FarShadow.ts`、`TerrainShadow.ts`、`Terrain.ts` |
| 砂紋のテクスチャと最高画質 | 砂紋を 1 画素ごとに計算せず、プレイヤーの周りに焼いたテクスチャで描く。立体のメッシュは最高画質だけ（§10） | `src/world/RippleMap.ts`、`Terrain.ts`、`Settings.ts` |

## 1. モデルの圧縮

モデルを作る道具（`npm run model:*`）が書き出す GLB（`src/assets/models/`、以下「元」）はそのまま残し、ゲームが読むのは圧縮版（`src/assets/models-packed/`）にした。

```bash
npm run models:pack        # 変わった元だけを圧縮する（4 並列。画像の変換結果は node_modules/.cache/higata-pack に残る）
npm run models:pack -- mahaze nets/net_small   # 名前で絞る
npm run models:check       # 圧縮版が元より古ければ失敗（npm run check と CI に入っている）
node tools/models/pack/compare.mjs [mahaze ...] # 元と圧縮版を同じ条件で描いて比べる（tests/smoke/out/pack-compare/）
```

- **テクスチャ**: KTX2（Basis Universal の UASTC、Zstandard、ミップマップ込み）。実行時に GPU が直接読める形式に変換される（PC と Steam Deck は BC7、スマホは ASTC か ETC2、どれもなければ非圧縮）。ノーマルマップは basisu の normal-map 設定、色は sRGB、それ以外（粗さ、遮蔽、模様の分布など）は線形で圧縮する
- **形状**: EXT_meshopt_compression（可逆。フィルターなし）
- glTF の中身は**番号ごとそのまま**残す。ハゼのヒーロー材質のように、extras がテクスチャを番号で指しているため（gltf-transform などで組み直すと番号がずれる）
- 圧縮のたびに、変換後のテクスチャを元に戻して PSNR を測り、30 dB を下回れば失敗にする。全 55 個の最低は 32.7 dB（128 px の細かいローレットのノーマルマップ）、ほとんどは 40〜55 dB
- ETC1S（もっと小さい形式）も比べたが、模様やノーマルマップが 26〜34 dB まで落ちるので使わない

結果（2026-10-12、55 個）:

| | 元 | 圧縮版 |
|---|---|---|
| ファイルの合計 | 289.6 MB | 311.0 MB |
| うち形状 | 約 106 MB | 約 36 MB |
| うちテクスチャ | 約 178 MB（PNG / JPEG） | 約 268 MB（UASTC + Zstandard） |
| テクスチャを全部 GPU に載せたとき | 約 2.5 GB（RGBA8 + ミップ、計 4.7 億画素） | 約 0.6 GB（BC7 / ASTC 4×4） |

ファイルの合計は 7 % 増える（JPEG だった画像が UASTC で大きくなるため）。読み込み後の GPU メモリと、テクスチャを GPU に送る時間は大きく減る。Web 版のダウンロード量を減らしたくなったら、UASTC の RDO（品質を少し落としてファイルを小さくする）を色のテクスチャに試す。

元と圧縮版の描き比べ（`compare.mjs`、モデルの写っている画素だけの PSNR）: 全 55 個で 28.9〜99 dB。いちばん低いのは lod2 のヒメハゼで、細いひれの条の「切り抜き」の境目が数画素ずれるため（見た目は同じ）。色空間の取り違えや形状の破損があれば 20 dB を大きく下回る。

モデルを作り直したら `npm run models:pack` を忘れずに（忘れると `npm run check` と CI が止まる）。

## 2. FSR 1 での拡大

PC（タッチ端末でない）の干潟では、

- 描画バッファ（キャンバス）は画面の画素数そのまま（約 4K まで）
- 3D の画は、画質の段階が決める大きさ（`maxDpr` と `maxPixels`、今までのキャンバスの大きさと同じ）で描く
- 小さく描いたときだけ、水の合成が画面に出すときと同じ仕上げ（three の ACES Filmic でのトーンマッピング、色の調整と周辺減光、sRGB 化）まで済ませた画を内部の大きさで書き、それを **EASU（拡大）→ RCAS（輪郭の補正）** で画面に出す。three はトーンマッピングと sRGB 化を画面に描くときしかしないので、その分は水のシェーダーが自分でする（`src/render/ToneMapGlsl.ts`）。拡大しないときと色は変わらない
- UI（HTML）とタモ網（最後に画面の解像度で上から描く）は拡大の影響を受けない

ホーム（水槽）、ショップ、スマホは今までどおり（キャンバスそのものを小さくし、ブラウザーが拡大する）。観察モード（ヒーロー材質）も内部の解像度で描き、最後の合成で画面に広げる。

確かめ方: `npm run build` のあと `node tests/smoke/upscale.mjs`。同じ景色を等倍、67 %、50 % で、FSR 1 と単純な拡大（bilinear）の両方で撮り、`tests/smoke/out/upscale-crops.png` に中央を 3 倍に拡大して並べる。デバッグパネル（F3）には `描画 1280×720 → 1920×1080 FSR` のように出る。

FSR 1 は AMD FidelityFX Super Resolution 1.0（MIT ライセンス）を GLSL に移したもの。ライセンス文は `src/render/Fsr.ts` の先頭にある。

## 3. 動的解像度と GPU 時間

- GPU 時間は `EXT_disjoint_timer_query_webgl2` で測る（Chrome / Electron のデスクトップ版にある）。デバッグパネルに `GPU 9.8 ms` と出る
- 目標: 段階「中」「高」は 60 fps、「低」「超軽量」は 30 fps
- GPU 時間が目標の 92 % を超えたら 5 % ずつ小さく、70 % を下回ったら大きくする（段階の大きさが上限、画面の 50 % が下限）。変えたあと 0.75 秒は次を変えない
- 小さくしても GPU 時間が減らないとき（CPU や頂点の処理で詰まっている）は 1 段戻して 20 秒そのまま
- GPU タイマーが無い環境では、遅れたフレームを見て下げるだけ（段階の大きさの 70 % まで）。上げるのは静かな時間が続いてから

## 4. 画質の自動設定

初めて干潟に入ったとき（PC のみ。その GPU で一度だけ）:

1. 動的解像度を止め、段階の大きさのまま 2.5 秒なじませてから 3 秒測る
2. GPU 時間が目標のフレーム時間の 1.3 倍を超えたら 1 段下げる（超軽量まで）。次の段階の目標の半分を下回ったら 1 段上げる（高まで。下げたあとは上げない）
3. 変えたら、その段階でもう一度測る（3 回まで）。決まったら知らせを出し、GPU の名前と一緒に保存する

確かめ方: `npm run build` のあと `node tests/smoke/auto-quality.mjs`（初回の測定・知らせ・保存・再読み込み・手動での解除と「自動」での測り直し）。この環境のソフトウェア描画（SwiftShader）でも GPU タイマーは使え、「超軽量」に決まる。

メニューの「干潟の画質」で段階を選ぶと自動は切れ、「自動」を押すと次に干潟に入ったときに測り直す。別の GPU（GPU の名前が違う）で遊ぶと、自動のままなら測り直す。初回の段階（測る前）は今までどおり GPU の名前から決める（内蔵 GPU なら「低」）。

## 5. 乾き具合

[判断記録](../planning/10_engine_decision.md) の §8-2 の 2 の 1 つめ。前は「最近の満潮線（1 時間に 5 cm ずつ下がる線）から下は一律に濡れている」という帯だった。今は、**その高さから潮が引いてからの時間**で、場所ごとに乾いていく。

- CPU（`src/world/WetDry.ts`）が潮汐モデルを 30 時間さかのぼり、干潟の高さごとに「潮が引いてからどれだけ乾かされたか」を計算する。日差しが強いほど速く乾き（夜は昼の 3 割ほど）、夏は冬より速い。結果は 256 段の帯状テクスチャ（RGBA8）にして、地形のシェーダーが高さで引く。時刻が 1 分以上進むか水位が 1 cm 以上動いたときだけ計算し直す（チケットやデバッグの時計で時刻が飛んでも、その時刻までに乾いたはずの状態になる）
- 乾き方は 2 段階、底質で速さが違う（「乾いた時間」の単位）:

  | | 砂 | 泥 |
  |---|---|---|
  | 表面の水膜（つや、空の映り込み） | 0.3 時間 | 1.2 時間 |
  | 含んだ水（暗さ、青み） | 2.5 時間 | 30 時間（干潮のあいだ、ほぼ乾かない） |

- 砂紋の谷と浅いくぼみは水膜が長く残る。水際のすぐ上は毛管水で湿ったまま（砂 8 cm、泥 50 cm）、水際の数 cm は染み出しの水膜で光る
- 低い干潟は地下水面が地表にあり、干潮のあいだも砂紋の谷とくぼみに水が残り、底質は水を含んだまま（水位から 25 cm まで。50 cm で消える。§9 で写真に合わせた）
- 引いた直後の砂紋の谷の水膜（東なぎさで足したもの）も、この水膜に含めた（谷ほど長く残る）。打ち寄せ波の記憶（`SurfMemory`）はそのまま上に重なる。漫湖の泥干潟（`uMudLook`）は自前の水の膜とつやを持つので、そこでは乾き具合の水膜と空の映り込みの強めを外す
- 水膜のあるところは、粗さ 0.07（空と太陽を映す）、砂粒やでこぼこの細かな凹凸は水に埋もれる（砂紋は残る）。遠くで砂紋が画素より細かくなると、谷の水膜は平均に寄せ、凹凸は粗さとして扱う（縞のちらつきを防ぐ）
- 空の映り込み: 地形の空の光は拡散光に合わせて弱く（`environmentIntensity` 0.03〜0.09）してあるので、濡れたところだけ鏡面反射を空そのままの強さに戻す
- 確かめ方: `npm run build` のあと `node tests/smoke/wetdry.mjs`（引き潮 2 時間前、干潮、2 時間後、夕方の干潮を同じ場所から撮る。`--turn 70` で潮だまりを外した向き、`--root <別のビルド>` で前の版と比べられる）

## 6. 色づくり（AgX）

[判断記録](../planning/10_engine_decision.md) の §8-2 の 2 の 2 つめ。トーンマッピングを ACES Filmic から **AgX** に替えた。

- どの経路も同じ式を通る（`src/render/ToneMapGlsl.ts`）: three が画面に描くもの（`CustomToneMapping` に組み込む）、FSR 1 に渡す水の合成、観察モードと水槽のヒーロー材質の仕上げ、図鑑のプレビュー
- AgX の見え方（look）は、今の画面の明暗（ACES で照明を合わせてある）を大きく変えないように当てはめた: 露出 ×2.55、power 1.6、彩度 1.1。灰色の階調は中間〜明部で ACES と数段階以内、中間調はわずかに明るく、明部はやわらかく丸まる。夕日のように明るく色の強い光が、ACES のように黄色や紫に転ばない
- 見比べ方: アドレスに `?tone=aces` を付けると前の ACES で描く（`?tone=agx` が今の既定）。`node tests/smoke/wetdry.mjs --tone aces --tag aces` と `--tone agx --tag agx` で同じ場面（干潟の昼〜夕方、西向きの夕日）を撮り比べられる
- AgX 本来の見え方（明暗をそのまま）にすると全体が眠くなり、照明の作り直しが要る。power を 2.7 まで上げると ACES の明暗にほぼ重なるが、暗部が潰れる（夜の場面）ので採らなかった
- 写真に合わせた空・濡れた地面・夕日の色は §9。LUT（色の調整表）は使わなかった（画面全体の色を後から変えるより、空・地面・夕方の光をそれぞれの計算の中で合わせたほうが、昼にも夕方にも効く）

## 7. TAA（時間方向のアンチエイリアス）

[判断記録](../planning/10_engine_decision.md) の §8-2 の 2 の 3 つめ。PC の干潟で、画質「中」「高」「最高」のときに使う（`QualityPreset.taa`。スマホと「低」「超軽量」は今までどおり）。

- カメラを毎フレーム 1 画素未満ずらして描き（Halton 2, 3 の 16 通り）、前のフレームまでの結果（履歴）と混ぜる（新しいフレームを 1 割）。履歴は深度とカメラの動きで今の位置に合わせ、周り 3×3 の色の平均と広がり（YCoCg）の範囲に収めてから混ぜる（動く生きものの残像を防ぐ）。カメラを速く回したところは新しいフレームを多めに、テレポートや観察モードから戻ったときは履歴を捨てる
- 履歴は Catmull-Rom で読む（混ぜるたびにぼけが積もらないように）
- 置く場所は、水の合成（画面の仕上げ）のあと、FSR 1 の前。拡大しないときも、最後に RCAS で軽く輪郭を立てる（TAA はわずかに柔らかくなるため）
- TAA を使うときは干潟の HDR バッファのマルチサンプリングを切る（その分は TAA が受け持つ）
- 静止画では MSAA 4 倍とほとんど同じに見える。効くのは歩いたり見回したりしているときの、遠くの砂紋やアマモのちらつき。カメラを回しながら撮っても残像は出ていない（`src/render/Taa.ts`）
- まだ: 生きものと水の動き（モーションベクトル）は使っていない。速く動くものは、周りの色の範囲に収める処理だけで残像を防いでいる

## 8. 影（近く・遠く・地形）

[判断記録](../planning/10_engine_decision.md) の §8-2 の 2 の 4 つめ。three の CSM（カスケード影）は、全材質の `onBeforeCompile` を置き換えて光の計算を書き換えるため、自作シェーダーの多いこのゲームとは合わない。そこで 3 つに分けた（影のある画質「中」「高」「最高」のみ。スマホと「低」「超軽量」は今までどおり）:

| | 範囲 | 細かさ | 描き直し | 落とすもの |
|---|---|---|---|---|
| 近くの影（three の影） | 64 m 四方。プレイヤーの前方へ 18 m ずらす（見ている所） | 2048 で 3 cm、1024 で 6 cm（前は 90 m 四方で 4.4 / 8.8 cm） | 毎フレーム | 生きもの、網、近くの石・牡蠣・マングローブ |
| 遠くの影（`FarShadow`） | マップ全体 | 2048 で約 15 cm | 太陽が 0.23° 動くか、プレイヤーが 20 m 動くか、30 秒ごと | 上に加えて、遠くの段階の護岸の石・牡蠣礁・マングローブ（`userData.farShadow`） |
| 地形の影（`TerrainShadow`） | マップ全体 | 512 四方（葛西で 62 cm） | 太陽が 0.17° 動いたとき | 土手、護岸の盛り上がり、砂の高まり、くぼみ |

- 近くの影は、テクセルの大きさごとに動かす（歩いても影のふちがちらつかない）
- 遠くの影は、地形のシェーダーが近くの影の届かない所だけで読む（2×2 のフィルター）。地形の影は、高さの地図を太陽に向かって GPU でたどって作り（最長約 500 m、太陽の大きさ 0.5° の半影）、地形のどこでも読む（地面はどちらの影の地図にも入らないため）
- 例: 葛西で太陽が西に 4° のとき、西の土手が干潟に約 70 m の影を落とす（`node tests/smoke/shadows.mjs` で地図を `tests/smoke/out/shadows-relief.png` に書き出して確かめている）
- まだ: 遠くの影と地形の影を受けるのは地形だけ（生きもの、水面、マングローブは近くの影だけ）。足元の接触影（画面上の深度から作る影）はまだ

## 9. 写真に合わせた見え方

プレイヤーから届いた干潟の写真 5 枚（2026-10-13。昼の干潮 2 枚: 積雲の下の砂紋、潮だまりのある泥干潟。夕日 2 枚: 望遠で、空はほぼ地平線のすぐ上だけ。夕方の逆光 1 枚: 広角）に合わせた。写真そのものは権利が分からないのでリポジトリに入れず、測った数字だけを `tools/grade/calibrate.mjs` に置いた。

- 測り方: 地平線を基準に 4 か所（空の上 15 %、地平線の上 1〜8 %、地平線の下 2〜15 %、下端 10 %）の平均色、青−赤、赤÷緑、明るさの広がり（90 % と 10 % の差）。ゲームは葛西の既定の干潟で、昼の干潮（低潮線から 30 cm の高さ、干潟に沿った向き）と、同じ日の 16:50（太陽に向けて）を撮って同じ所を測る。`npm run build` のあと `node tools/grade/calibrate.mjs [組み合わせ.json]`
- 前の見え方との差（点数。小さいほど写真に近い）: 445 → 222

| | 前 | 写真 | 今 |
|---|---|---|---|
| 昼の空の上（色） | 156,190,215（白っぽい） | 136,180,214 | 147,194,222 |
| 昼の地平線の下（明るさの広がり） | 15（一様な灰色） | 120 | 70（水膜に空と雲が映る） |
| 昼の足元 | 111,115,120 | 60,75,88 | 84,98,114 |
| 夕方の空の上（赤÷緑） | 0.57（青緑） | 1.05（くすんだ藤色） | 0.80（青〜紫） |
| 夕方の地面（赤÷緑） | 1.03（灰色） | 1.30（夕焼けを映す） | 1.21 |

変えたもの:

- **オゾン**（`src/world/Sky.ts` の `ozoneTransmittance`）: 空のモデル（Preetham）にはオゾンが入っていない。夕方の空が青緑になるのはそのため（実際は、層を横から通る日の光からオゾンが橙と緑を抜くので、夕焼けの上の空は青く残る）。高さ 25 km の殻を日の光が通る長さで透過率を出し、空の散乱光に掛ける（太陽が沈んだあとは層を 2 回通る）。量は実際の 1.5 倍
- **空**: 明るさ ×0.27（前 0.32）、彩度 1.4（夕方は 1.0 に戻す。夕焼けが濃くなりすぎる）、レイリー 3（前 2.2）、濁り 1.8、夕方は +10 と Mie +0.012（もやで夕日の周りが広く明るい）。彩度を上げても色が負にならないようにした（赤い太陽の円盤の青が負になり、水面の太陽の映り込みが真っ赤な線になっていた）
- **夕方の仕上げ**: 太陽が −5〜14° のあいだ、画面全体を少し暖色に（×1.05, 0.95, 0.85。昼光に合わせたカメラが夕日の光を撮ったとき）。空からの環境光（半球光）も夕方は暖色に半分寄せる
- **濡れた地面**（`Terrain.look`）: 水を含んだ底質の暗さを乾いたときの 0.45 倍（前 0.66）。低い干潟の地下水面（§5）: 水位から 25 cm までは谷とくぼみに水膜、底質は水を含んだまま。遠くの水膜の粗さは 0.3 のまま（0.15 にしても点数はほとんど変わらず、TAA のない画質で縞がちらつく）
- 合わせなかったもの: 夕方の空の上が写真ほどくすまない（写真は薄雲ともやが多い日。晴れた日の夕方の上空は青いのが本当）。昼の地平線のもやは写真より少し白い

## 10. 軽量化（2026-10-13）

最新の main を、画質ごとに読み込み量・描画の回数・三角形と、機能を 1 つずつ止めたときのフレームの時間で測った（SwiftShader、640×360 と 1280×720。実機の数字ではないので割合で見る）。重かったのは、足元の砂紋のメッシュ（フレームの約 4 割。高で 108 万三角形、低でも 35 万）と、地形のシェーダー（砂紋の場を 1 画素ごとに値ノイズ約 54 回・ハッシュ約 90 回で計算。画素の多い画面ほど効く）。

- **最高画質を新設**（PC の干潟だけ。自動設定では選ばない）: 高に、足元の砂紋を立体で描くメッシュ（半径 4 m）を足し、大きな画面を本来の解像度で（DPR 2、830 万画素まで）、近くの生きものの詳細を 8 体に。**それ以外の画質ではメッシュを使わず**、地面に描く
- **砂紋をテクスチャに焼く**（`src/world/RippleMap.ts`）: 砂紋の場（うねる峰、分かれと合流、出来具合、非対称）を、プレイヤーの周りの 2 枚のテクスチャに一度だけ計算して入れる。近く 1.1 cm 刻みで 22 m 四方、遠く 3 cm 刻みで 61 m 四方（超軽量は 1.6 cm・16 m と 3.5 cm・36 m）。中身は砂紋の高さと、陰影の傾き。歩いて窓がずれた分（0.7 m ごと）だけ帯で描き足す（窓は巻き戻して使う）。地形のシェーダーは 1〜2 回読むだけ。最高のメッシュの頂点も同じテクスチャを読む（頂点ごとのノイズ計算がなくなった）。メッシュのない画質では、足元 4 m の陰影に、砂紋の起伏そのものの傾き（メッシュの面が見せていた分）を足す
- **地形のシェーダーの残り**: 巣穴と細かい凹凸は、画素が見分けられる大きさのときだけ計算（見た目は同じ）。浅い水底の光の網は、画素が網目より大きいときは平均だけ（波の曲率の計算を飛ばす）。砂紋のない漫湖では砂紋を読まない
- **シェーダーの準備**: three が各プログラムの初回にリンクの結果を問い合わせて待つ処理（`debug.checkShaderErrors`）は、開発中とテストの自動操作のときだけ。干潟のシェーダーを用意する前に空と環境マップを作る（なかったので、全材質を環境マップなしで用意し、最初のフレームでもう一度作っていた）。コメツキガニの下準備が、群れの分だけでなく干潟の全体を画面用の組み合わせで用意していたのを直した。干潟の中のシェーダーは 中で 148 → 113 個
- コメツキガニの群れが干潟の画質ではなく古い共通の設定を見ていたのを直した（超軽量でも中と同じ数）

## 11. 軽量化 2（2026-10-14）

葛西のカニの群れの中（干潮、画質「中」、1280×720、SwiftShader）で、何がフレームを食っているかを測り直した。物を 1 つずつ隠す・シェーダーの一部を差し替えるたびに、その前後のフレーム時間を交互に測る（隠す前・隠した後・戻した後。前後の 2 回の差で揺らぎを見る）。

| 何を止めたか | フレームの時間の減り |
|---|---|
| 水の合成を単なるコピーにする | 40 % |
| 　そのうち、波打ち際の surf のコードをコンパイルしない（葛西には surf がない） | **33 %** |
| 　波の向き（20 本） / 水際のノイズ / 屈折 / きらめき | 9 % / 4 % / 3 % / 0 % |
| 　水のある画素の処理を飛ばす（実行時の分岐） | 0 % |
| 地形のシェーダーを素の標準材質にする | 30 % |
| 　泥干潟の見た目のコードをコンパイルしない（葛西にはない） | 3 % |
| 　近くの砂粒 / 水膜・くぼみ・珪藻のノイズ / 巣穴 / 細かい凹凸 | 3 % / 5 % / 1 % / 1 % |
| 地形の網を全部いちばん粗く | 10 % |
| コメツキガニの群れ（そのうち砂団子 8 %） | 7〜13 % |
| 太陽の影 | 5〜11 % |
| 半分の解像度 | 46〜55 % |

- **一番重かったのは、使っていないコード**: 水の合成のシェーダーは、走水の波打ち際（surf: 砕ける波、遡上、泡）のコードを、surf のない葛西や漫湖でも全部持っていた。実行時の分岐で飛ばしてはいても、シェーダーが大きいだけで全部の画素が遅くなる（GPU では同時に動かせる画素が減る）。水のある画素の処理を実行時に飛ばしても速くならず、コードを外すと 3 分の 1 速くなったのはそのため。surf のない浜では `NO_SURF` で `uSurf` を定数 0 にしてコンパイルから外す（`Surf.ts` の `SURF_GLSL`、`WaterPass`）。見た目は変わらない（葛西・漫湖の `uSurf.w` はもともと 0）
- 地形も同じく、泥干潟（漫湖）の見た目のコードを、それのない葛西・走水では外す（`NO_MUD`、`Terrain.setSediment`。葛西は layout がないので既定で外す）
- 遠くの砂団子（8 枚・20 枚の形、1〜2 画素）は、こぶの形と法線を出すノイズ（頂点 1 つに 3D ノイズ 8 回）を省いた材質で描く（`makePelletMaterial({ simple: true })`）
- 結果（同じ場所・同じ視点を、本流とこの変更で交互に 2 回ずつ）: カニの群れの中 2,598 → 1,652 ms（36 % 減）、堤防ぎわの出発点 2,502 → 1,615 ms（35 % 減）。描く回数と三角形は同じ（シェーダーの中身だけの差）
- 残っている大きいもの: 地形のシェーダー（ノイズが多くのブロックに分かれていて、1 つだけ大きいものはない）、太陽の影（受け側の影の読み取り）。どちらも見た目を変えずに削るには、ノイズをテクスチャに焼くなどの作り直しが要る
- 測り方: ソフトウェア描画では、物を隠すと水面がその分の画面を覆う（地形を隠すと、そこが全部水になる）ので、「隠す」ではなく「材質を素のものに替える」「コードを外す」で測った方が当たる
